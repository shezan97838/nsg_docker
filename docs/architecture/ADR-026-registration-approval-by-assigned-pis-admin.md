# ADR-026: Registration approval belongs to the PIS Admin the personnel record is assigned to

Status: accepted (2026-11-07). Supersedes the approver role of ADR-015 (`REGISTRATION_ADMIN`). Builds on ADR-016/017 (Admin Portal), ADR-024 (`RequirePisAdminPortal`) and the `users_pis.assigned_to` column (migration `Add_PIS_Personnel_AssignedTo`).

## Decision
Approving or rejecting a mobile registration request is done by the **PIS Admin the person's personnel record is currently assigned to**. `REGISTRATION_ADMIN` is no longer part of the workflow.

- **Authorization:** both endpoints (`GET` and `PUT {id}/decision` of `api/v1/mobile-approval-requests`) use `RequirePisAdminPortal` (AdminBearer + `PIS_ADMIN` + live admin session). A legacy staff `Bearer` token (any role name) gets 401; Super Admin, Registration Admin and every other role get 403; anonymous gets 401. The `RequireRegistrationAdmin` policy was removed. The `REGISTRATION_ADMIN` role row, its id and its accounts are untouched (it can still sign in and call `GET api/v1/admin/auth/me`).
- **Ownership source:** `approve_mobile_users.nsg_number` -> `users_pis.nsg_number` -> `users_pis.assigned_to`, read live on every call. Never `created_by`, never the upload batch, never a body value, never a copy stored on the request. An ownership transfer therefore needs no change to any approval row: pending requests move to the new owner at the moment `assigned_to` changes.
- **List:** the ownership condition is part of the query (inner join on the personnel row, `assigned_to = admin_profile_id`) and is applied before status, search, count and paging. Requests of unassigned, other admins' or missing personnel are never returned.
- **Decision:** `ApproveMobileUserRepository.DecideAsync` runs in one transaction whose FIRST statement is a conditional `UPDATE users_pis SET assigned_to = <caller> WHERE assigned_to = <caller> AND <this request's nsg_number>`. It changes no data but locks the personnel row until commit, so a concurrent transfer either committed first (no match: 403, nothing written) or waits for the decision to finish. Only then is the Pending request claimed (`UPDATE ... WHERE approval_status = Pending`, first decision wins, 409 otherwise) and `users_pis.mobile_app_activation_status` updated. Lock order is always `users_pis` row, then `approve_mobile_users` row; no other code path takes them in the opposite order.
- **Responses:** not the owner, or unassigned: 403 "This registration request is not assigned to you." (the same text for both, and decided before the request's status is looked at, so a non-owner learns nothing about it). Missing request: 404. Missing personnel record: 409 (unchanged). Already decided (owner): 409 (unchanged). No usable `admin_profile_id`: 401.

## Reviewer identity and `approved_by`
`approved_by` and `updated_by` are `int` columns; `admin_profiles.id` is `bigint`. The ownership comparison is done in `long` everywhere. Writing the reviewer into the int column is guarded: an admin id above `int.MaxValue` is refused (401, nothing written) and the repository additionally uses a checked conversion, so an id can never be truncated into a different admin. Staff user ids no longer reach this column (staff tokens are refused), so the earlier staff/admin ambiguity of `approved_by` ends for new rows; old rows may still hold staff ids.

**Smallest safe correction, not done (needs a migration and approval):** widen `approve_mobile_users.approved_by` and `updated_by` to `bigint`. `ReviewerIdentityResolver` (with its Development-only `AsmarTest` fallback) is no longer used by this service.

## Consequences
- Until the Super Admin ownership-transfer API exists, only records that have an owner (inserted through the PIS APIs or uploads after the ownership change) can be decided. Every pre-existing record is unassigned, so its requests are invisible and cannot be decided by any PIS Admin. This is by design and is not backfilled.
- A PIS Admin who is deactivated keeps ownership; their requests wait until a transfer.

## Ownership transfer by the Super Admin (added 2026-11-07)
`POST api/v1/admin/pis-personnel/transfer-ownership` (`PisOwnershipController`, `RequireSuperAdmin`, Admin Portal SUPER_ADMIN only) gives one personnel record to a PIS Admin. Request: `personnelNsgNumber`, `targetPisAdminNsgNumber`, optional `reason`. It grants the Super Admin no read, update, delete, upload or approval access to personnel data.

- **Target rules:** an existing, active, fully activated Admin Portal account whose role is exactly `PIS_ADMIN` (404 unknown, 409 inactive or not activated, 400 any other role, including Super Admin). The target's `admin_profiles.id` is what is stored in `users_pis.assigned_to`.
- **Transaction (`PisOwnershipRepository.TransferAsync`):** the first statement is a no-op conditional write on the `users_pis` row that holds its lock until commit; the current owner is read after it; the same owner is a 200 no-op with no history; the target is re-verified; then only `assigned_to` is updated (`ExecuteUpdate`, so `created_by`, `updated_by` and `updated_at_ist` stay) and a `pis_ownership_transfers` row is appended in the same transaction. Lock order is the personnel row only, which composes with a registration decision (personnel row, then approval row); neither can deadlock the other.
- **History:** table `pis_ownership_transfers` (migration `Add_PIS_Ownership_Transfers`, generated, NOT applied): `pis_record_id`, `nsg_number`, `previous_assigned_to` (null = was unassigned), `new_assigned_to`, `transferred_by` (the Super Admin's `admin_profile_id` from the token), `reason`, `transferred_at_ist`. Append-only, no foreign keys, like the other PIS tables.
- **Approvals:** nothing is rewritten. A pending request leaves the old owner and appears for the new one because the list and the decision read `users_pis.assigned_to` live.
- **Races with PIS Admin edits:** `UserPisRepository.UpdateAsync` (used by `PUT` and `DELETE` of `api/v1/users-pis`) now runs in a transaction whose first statement is the same conditional lock on `assigned_to = <caller>`, so an edit loaded before a transfer cannot be saved after it (`PisSaveOutcome.NotOwner`, 403). The Excel path already had this guard.
